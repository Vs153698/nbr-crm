01 Domain plan

Three hostnames, each with one job.

HostnameServesWho talks to it
crm.codenitti.in The CRM interface, and the API under /api Staff browsers. This is the only address anyone types.
api.codenitti.in The same API container The .org site's server, pushing signed webhooks. Server-to-server only — nobody opens this in a browser.
nationalbookofrecords.org The existing public site and its admin The public, and the CRM pushing payments, certificates and dispatch back.
Staff browser→ crm.codenitti.in→ SPA + /api → API
nationalbookofrecords.org→ api.codenitti.in→ API
API→ nationalbookofrecords.org→ /api/crm-connector/…

Both CRM hostnames point at the same Coolify application. There is only ever one API container; it simply answers on two names.

02 The routing decision — read before you configure anything

This is the one architectural constraint that will silently break sign-in if you get it wrong, so it comes before the Coolify steps.

The browser must reach the API on crm.codenitti.in, not api.codenitti.in. Two facts in the built frontend force this, and neither is configurable at deploy time:

1. The API base is a hardcoded relative path — const API_BASE = '/api/v1' in apps/web/src/lib/api-client.ts. There are no VITE_ variables anywhere in the web app, so the built bundle cannot be pointed elsewhere.

2. Every request is sent with credentials: 'same-origin'. If the SPA on crm.codenitti.in called api.codenitti.in, the browser would attach no cookies at all and every request would come back unauthenticated — a login that appears to succeed and then immediately fails.

What this means in practice

Serve the SPA at crm.codenitti.in and have that same host forward /api/* to the API container. The browser then sees one origin, the SameSite=strict cookies work exactly as intended, and CORS never enters the picture because there is no cross-origin request to permit.

api.codenitti.in still earns its place: it is what the .org server posts its signed webhooks to. That traffic carries an HMAC signature rather than a cookie, so origin and CORS are irrelevant to it.

If you would rather the browser call api.codenitti.in directly, that is a code change, not a configuration change: introduce a VITE_API_BASE_URL, switch the three credentials: 'same-origin' call sites to 'include', set COOKIE_DOMAIN=.codenitti.in, and add https://crm.codenitti.in to CORS_ORIGINS. It works — the two hosts share a registrable domain, so SameSite=strict still applies — but it is more moving parts for no gain. Section 7 takes the proxy route.

03 Postgres and Redis in Coolify

  1. New Resource → PostgreSQL 16 in your project. Coolify generates the credentials. Copy the internal connection string — the one using the service name, not a public host.
  2. New Resource → Redis 7. Same again: take the internal URL.
  3. Leave both without a public domain. They only ever need to be reachable from the API container on Coolify's internal network.

The internal URLs look like this, with the service names Coolify assigns:

# DATABASE_URL
postgresql://nbr:<generated-password>@<postgres-service-name>:5432/nbr_crm

# REDIS_URL
redis://:<generated-password>@<redis-service-name>:6379

Sessions live in Redis. Losing or flushing it signs everyone out. That is recoverable — people sign in again — but do not point it at a shared Redis that something else flushes on a schedule.

04 Generating secrets

Generate these on your own machine and paste them into Coolify. Do not commit them anywhere.

# Two DIFFERENT JWT secrets. The API refuses to start if they match, because one
# shared secret would let an access token be replayed as a refresh token.
openssl rand -base64 48    # → JWT_ACCESS_SECRET
openssl rand -base64 48    # → JWT_REFRESH_SECRET

# 32 bytes, base64, for encrypting Aadhaar / passport / bank details at rest.
openssl rand -base64 32    # → PII_ENCRYPTION_KEY

# The shared secret between the CRM and the .org site. Minimum 16 characters.
openssl rand -hex 32       # → NBR_WEBHOOK_SECRET

# A real password for the first admin. It is forced to change at first login.
openssl rand -base64 18    # → SUPER_ADMIN_PASSWORD

The webhook secret goes in three places and all three must be byte-identical. This is the most common integration failure by a wide margin.

#WhereUsed for
1Coolify → API app → NBR_WEBHOOK_SECRET Verifying webhooks arriving from the .org site.
2CRM UI → Settings → integration secret Signing pushes going to the .org site.
3.org admin → Settings → Internal CRM → shared secret Both signing and verifying on that side.

Paste with no surrounding quotes and no trailing newline. Both systems expose a fingerprint of the secret they hold, so you can compare them without either side revealing the value.

Losing PII_ENCRYPTION_KEY makes the encrypted identifier columns unrecoverable. Store it in a password manager, separately from the database backups. A backup you cannot decrypt is not a backup.

05 The API application

  1. New Resource → Application, pointed at this repository, on the branch you deploy from. Base Directory: / — it is a pnpm workspace and the build must run from the root, not from apps/api.
  2. Build Pack: Nixpacks. There is no Dockerfile in the repo.
  3. Install command 
    corepack enable && pnpm install --frozen-lockfile
  4. Build command — the shared package must be built before the API, because the API imports its compiled output. 
    pnpm --filter @nbr/shared build && pnpm --filter @nbr/api build
  5. Start command 
    pnpm --filter @nbr/api start:prod
  6. Port: 4100, matching API_PORT. The app binds 0.0.0.0, so it is reachable inside the container network without further work.
  7. Health check path: /health not /api/v1/health — the health routes are deliberately excluded from the global prefix and are version-neutral.
  8. Domains: add both, comma-separated. 
    https://api.codenitti.in,https://crm.codenitti.in/api
    The second entry is what puts the API on the same origin as the SPA.

Check whether Coolify's proxy strips the path prefix. If the /api route arrives at the container with /api already removed, every request 404s, because the application genuinely expects to be served under /api. Verify with the curl in section 12 before going further — if it 404s, remove the strip-prefix middleware on that route, or use the nginx approach in section 7 instead, which leaves the path untouched.

Run exactly one instance. The scheduled jobs — the evening sales report, payment reminders, the retention sweep — are not leader-elected, so a second replica sends everything twice.

07 The frontend application

A static build plus a proxy. The proxy is the part that matters.

Build settings

  1. New Resource → Application, same repository and branch. Base Directory: /.
  2. Install command 
    corepack enable && pnpm install --frozen-lockfile
  3. Build command — again, shared first. 
    pnpm --filter @nbr/shared build && pnpm --filter @nbr/web build
  4. Publish / output directory: apps/web/dist
  5. Domain: https://crm.codenitti.in
  6. Enable SPA mode (Coolify's "Is it a SPA?" toggle, or an equivalent try_files fallback). Without it, refreshing on /applicants/123 returns 404 — React Router owns those paths, not the web server.

Routing /api to the API

Two ways, depending on how section 5's path routing behaved:

Option A — Coolify path routing try first

You already added https://crm.codenitti.in/api as a second domain on the API app in section 5. If the curl in section 12 returns a JSON envelope rather than a 404, you are done — nothing further is needed here.

Option B — serve the SPA from nginx and proxy deterministic

If the path route 404s or strips the prefix, deploy the frontend as a Dockerfile application instead of a static site. This leaves the path completely untouched, and you own the behaviour rather than inferring it.

# Dockerfile at the repository root
FROM node:22-alpine AS build
WORKDIR /app
RUN corepack enable
COPY . .
RUN pnpm install --frozen-lockfile \
 && pnpm --filter @nbr/shared build \
 && pnpm --filter @nbr/web build

FROM nginx:alpine
COPY --from=build /app/apps/web/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
# nginx.conf — <api-service> is the API application's internal Coolify name
server {
  listen 80;

  location /api/ {
    proxy_pass         http://<api-service>:4100;
    proxy_http_version 1.1;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;

    # Evidence and record videos: MAX_UPLOAD_MB is 200.
    client_max_body_size 220m;
    proxy_read_timeout   300s;
  }

  location / {
    root      /usr/share/nginx/html;
    try_files $uri $uri/ /index.html;
  }
}

Note the trailing slash on both location /api/ and the proxy_pass target being absent — that combination forwards the full original path, which is what the API expects.

08 Frontend environment

The frontend takes no environment variables at all. There is not a single import.meta.env reference in apps/web/src. The API base is the hardcoded relative path /api/v1, and everything else the app needs — organisation details, packages, categories, templates, feature permissions — it fetches from the API at runtime.

So there is nothing to configure on the frontend application beyond the build command, the output directory, the domain and the SPA fallback. Leave the Environment Variables tab empty.

VariableScopeStatus
VITE_API_TARGETLocal development only Not used in production It configures the Vite dev-server proxy in vite.config.ts and has no effect on a built bundle.

The consequence worth remembering: because the API address is baked in as a relative path, moving the API to a different hostname later is a code change and a rebuild, not an environment change. That is the trade-off behind the routing decision in section 2.

09 Migrate and seed

Once, after the first successful API deploy.

Run these from Coolify's terminal / execute-command against the API container, so they use the same environment and internal network as the app:

# Create the schema. Additive and safe to re-run — it applies only what is missing.
pnpm --filter @nbr/api db:migrate

# Reference data plus the first Super Admin: roles, permissions, statuses,
# templates, couriers, packages, categories, settings.
# Creates NO applicants and NO applications.
pnpm --filter @nbr/api db:seed

On every later release, run db:migrate again after the deploy. Migrations are written to be additive, so most releases need no maintenance window.

If Coolify's terminal is awkward for your setup, the same two commands work as a pre-deployment command on the API application. Make it db:migrate only — seeding on every deploy is harmless because it is idempotent, but it is noise you do not need.

10 Changes on nationalbookofrecords.org

The complete list. It is short because the brief was that the customer-facing system keeps behaving exactly as it does today.

10.1 — Environment: nothing to change no action

The connector reads no environment variables. Its three settings — whether sync is on, the CRM's address, and the shared secret — are rows in the site_settings table, edited through the admin panel. Every existing variable on that site — DATABASE_URL, JWT_SECRET, the R2 keys, SMTP, Razorpay, Redis — stays exactly as it is.

Two existing variables are worth confirming rather than changing, because the links the CRM shows back into the site are built from them:

VariableShould be
API_URLThe site's real public API address on nationalbookofrecords.org.
FRONTEND_URLhttps://nationalbookofrecords.org

10.2 — Deploy the connector branch action

It adds files and appends one line to a few existing handlers. No existing endpoint changes its request or response shape.

What it addsWhere
Signing, verification and push helpersbackend/src/lib/crmSync.ts, crmSyncPayload.ts
The connector routesbackend/src/routes/crmConnector.ts
One fire-and-forget line each in approve, manual payment, certificate issue, payment settle and dispatch updateexisting route files
The Internal CRM settings tabsrc/pages/admin/AdminSettings.tsx, CrmSyncPanel.tsx

The hooks cannot break the site. Each is a single non-throwing, detached call. If the CRM is down, unreachable or misconfigured, the approval or payment still succeeds and the failure is written to the sync log.

10.3 — Run the migration action

cd backend && pnpm db:migrate

Additive only: it creates crm_sync_log and inserts three site_settings rows — crm_sync_enabled (false), crm_base_url (empty), crm_secret (empty). No existing table is altered. With sync left off, the site behaves precisely as before.

10.4 — Allow outbound access action

The .org server must be able to reach https://api.codenitti.in, and the CRM container must be able to reach https://nationalbookofrecords.org. If you put Coolify behind an IP allowlist, add the .org server's egress addresses to it.

10.5 — Check the clocks action

Signatures are rejected outside a 300-second window. Confirm NTP is running on both hosts. The Test connection button reports the measured difference, so this diagnoses itself.

11 Connecting the two

CRM side first, so the .org site has something to talk to.

On the CRM — https://crm.codenitti.in

  1. Sign in as the Super Admin and change the temporary password. This signs you out everywhere; sign in again with the new one.
  2. Open Settings and set the integration base URL to https://nationalbookofrecords.org, paste the same shared secret that is in NBR_WEBHOOK_SECRET, and switch it on.
  3. Run sync packages and sync categories, so the CRM's dropdowns mirror the website's. Do this before anyone raises a payment — otherwise operators are offered prices the .org site will reject.

On the .org admin

  1. Open Settings → Internal CRM.
  2. Set the CRM base URL to https://api.codenitti.in not crm. — this is the server-to-server hop, and it posts to /api/v1/integrations/nbr-website/applications under that host. No trailing slash, no quotes, no stray whitespace.
  3. Paste the same shared secret and switch sync on.
  4. Press Test connection. If it fails, compare the two secret fingerprints — if they differ, the secrets differ.
  5. Press Backfill to send every approved-and-beyond application. Safe to re-run; nothing is duplicated.

Backfill sends approved applications and everything past that point. Pending, under-review and draft applications are deliberately excluded — they belong to the .org site until somebody approves them.

12 Verifying

First, prove the routing

This is the check that decides between Option A and Option B in section 7. Run it before anything else:

# Expect an HTTP 401 with a JSON envelope — that means the request reached the app.
# A 404 means the path prefix is being stripped or not routed. Go to Option B.
curl -i https://crm.codenitti.in/api/v1/auth/me

# The API's own health route, on its server-to-server hostname.
# Note it is NOT under /api/v1 — health is excluded from the global prefix.
curl -i https://api.codenitti.in/health
The CRM alone
  • The API container starts with no environment complaints in the deploy log.
  • https://crm.codenitti.in loads the sign-in screen.
  • Signing in works — and stays signed in after a page refresh. If it signs you straight back out, the routing in section 2 is wrong.
  • Refreshing on a deep link such as /applicants loads the page rather than a 404, confirming the SPA fallback.
  • First login forces a password change, and the new password works.
  • Creating an applicant succeeds and the category list shows the .org site's categories.
  • Uploading a file succeeds and downloading it returns the same file.
  • A test email arrives and is not marked as spam.
.org → CRM
  • Test connection reports success.
  • Approving an application on the .org site makes it appear in the CRM within seconds, at Selected.
  • Recording a manual payment there shows it in the CRM against the right package and price.
  • Updating dispatch there updates the CRM's Dispatch tab.
CRM → .org
  • Recording a payment in the CRM shows it on the .org application.
  • Issuing a certificate in the CRM puts the number on the .org site.
  • Updating dispatch in the CRM mirrors the courier and tracking number.
  • An applicant created in the CRM does not appear on the .org site. This is correct and deliberate.

13 Troubleshooting

SymptomCauseFix
Sign-in succeeds, next request is 401, back to the login screen The browser is reaching the API on a different origin, so credentials: 'same-origin' sends no cookies. Route /api through crm.codenitti.in — section 2 and section 7.
curl https://crm.codenitti.in/api/v1/auth/me returns 404 The proxy is stripping the /api prefix, or not routing that path. Remove the strip-prefix middleware, or switch to Option B in section 7.
Container exits at startup listing variables Environment validation failed — it reports every problem at once. Fix each line it names. It is telling you exactly what is wrong.
JWT_REFRESH_SECRET must differ from JWT_ACCESS_SECRET Both JWT secrets hold the same value. Generate a second, different one.
COOKIE_SECURE must be true in production Production without secure cookies. Set it to true. Coolify terminates TLS for you. Do not disable the check.
Health check never goes green Coolify is checking /api/v1/health. Use /health — it is excluded from the global prefix.
Build fails on a missing @nbr/shared type The shared package was not built before the app that imports it. Keep pnpm --filter @nbr/shared build first in the build command.
Refreshing a deep link gives 404 No SPA fallback on the static site. Enable SPA mode, or the try_files line in Option B.
WEBHOOK_SIGNATURE_INVALID (401) The secrets differ, or a proxy rewrote the request body. Compare fingerprints on both sides. Ensure nothing in front of the API modifies bodies.
timestamp outside tolerance Clock drift beyond 300 seconds. Fix NTP on both hosts. Test connection reports the measured difference.
Large uploads fail A proxy body limit below MAX_UPLOAD_MB. Raise it above 200 MB on whatever sits in front of the API.
Payment push rejected by the .org site The package is CRM-only and carries no plan code. Run the package sync so both catalogues match.
Everyone signed out at once Redis restarted or was flushed. Expected — sessions live there. Users sign in again.
Two evening sales reports More than one API replica running the scheduler. Scale the API application back to one instance.

Where to look, in order

  1. Coolify → the API application → Logs. Every failed push is logged with its HTTP status and the response body.
  2. .org admin → Settings → Internal CRM → sync log. Both directions, with the outcome and reason for each.
  3. CRM → Audit Logs. Confirms whether the action was recorded at all, and who performed it.
