01 The short answer about the existing site

Because this is the question that prompted the document, here it is first.

No environment variable changes are required on the existing website. The connector reads none. Its three settings — whether sync is on, the CRM's address, and the shared secret — are stored in the site_settings table and are set through the admin panel at Settings → Internal CRM.

What the existing site does need is a database migration (it adds one table and three settings rows, and touches nothing else), a deploy of the connector branch, and outbound network access to the CRM. Section 8 covers all three.

The full list of what changes on the existing site is deliberately small, because the brief was that the customer-facing system keeps working exactly as it does today. Nothing in its existing environment is touched.

02 What you are deploying

The CRM is four processes and three stores

APINestJS on Node 22. Serves /api/v1. Runs the scheduled jobs.
WebReact SPA built by Vite to static files. No server of its own.
PostgreSQL 16All application data.
Redis 7Sessions, cache, rate limits, job queue.
S3-compatible storageCloudflare R2 in production. Evidence, certificates, PDFs.
SMTPOutbound email. Any provider.

The SPA and the API must be served from the same origin. The web app calls /api/v1 as a relative path, and the auth cookies are SameSite=strict. Putting the API on a different hostname breaks sign-in. Section 7 shows the reverse-proxy layout.

How the two systems talk

DirectionCallerEndpoint on the receiver
Website → CRMWebsite backendPOST /api/v1/integrations/nbr-website/applications
CRM → WebsiteCRM APIPOST /api/crm-connector/{payment,certificate,dispatch}
CRM → WebsiteCRM APIGET /api/crm-connector/{plans,categories}

Every call is signed with HMAC-SHA256 over the timestamp and the raw body, and rejected if the timestamp is more than 300 seconds from the receiver's clock. Both servers need working NTP.

03 Prerequisites

  • Node.js 22 or newer and pnpm 11.15.1 (corepack enable is the easiest route).
  • PostgreSQL 16 — hosted in India, see the note below.
  • Redis 7.
  • An S3-compatible bucket — Cloudflare R2 with an Object Read & Write token.
  • SMTP credentials that can send as your organisation's domain.
  • TLS on the CRM hostname. Non-negotiable: the API refuses to start in production without secure cookies.
  • Outbound HTTPS from the website's server to the CRM, and from the CRM to the website.

Data residency. DPDP_DATA_REGION defaults to IN and the API checks the database host against it at boot. Host Postgres and the object storage bucket in India. This is a DPDP Act, 2023 posture decision, not a performance one — do not "fix" a boot failure here by weakening the setting.

04 Generating secrets

Generate these once, store them in your secret manager, and never commit them.

# Two DIFFERENT JWT secrets — the API refuses to start if they match,
# because a shared secret lets an access token be replayed as a refresh token.
openssl rand -base64 48   # → JWT_ACCESS_SECRET
openssl rand -base64 48   # → JWT_REFRESH_SECRET

# 32 bytes for encrypting Aadhaar / passport / bank details at rest.
openssl rand -base64 32   # → PII_ENCRYPTION_KEY

# The shared secret between the CRM and the website.
openssl rand -hex 32      # → NBR_WEBHOOK_SECRET

The webhook secret goes in three places and all three must match exactly. This is the single most common cause of a failed integration.

#WhereUsed for
1CRM environment → NBR_WEBHOOK_SECRETVerifying pushes arriving from the website.
2CRM settings → integration secretSigning pushes going to the website.
3Website admin → Settings → Internal CRM → shared secretBoth signing and verifying on that side.

Paste it with no leading or trailing whitespace and no surrounding quotes. Both sides expose a fingerprint of the secret they hold so you can compare them without revealing either.

06 Build and first run

# 1 — install and build all three packages in dependency order
pnpm install --frozen-lockfile
pnpm build

# 2 — create the schema. Safe to re-run; it only applies what is missing.
pnpm db:migrate

# 3 — seed reference data and the first Super Admin.
#     Creates roles, permissions, statuses, templates, couriers and settings.
#     Creates NO applicants and NO applications.
pnpm db:seed

# 4 — start the API
cd apps/api && pnpm start:prod

The SPA build lands in apps/web/dist as static files. Serve it from your web server or upload it to your CDN — it needs no Node process.

If the API refuses to start, read the error. It validates the whole environment before listening and prints every problem at once, each naming the variable and what is wrong with it. It is telling you exactly what to fix.

Running it as a service

Use systemd, PM2 or your platform's process manager against node dist/main.js in apps/api with NODE_ENV=production. Restart on failure, and make sure the working directory is apps/api so the correct .env is found.

Run exactly one API instance for now. The scheduled jobs — the evening sales report, payment reminders, the retention job — are not leader-elected, so a second instance sends everything twice.

07 Reverse proxy

One hostname, two backends. This layout is what keeps the auth cookies working.

# nginx
server {
  listen 443 ssl http2;
  server_name crm.example.in;

  # API — everything under /api goes to the Node process
  location /api/ {
    proxy_pass         http://127.0.0.1:4100;
    proxy_http_version 1.1;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;

    # Evidence and record videos are large; the app allows up to 200 MB.
    client_max_body_size 220m;
    proxy_read_timeout   300s;
  }

  # SPA — static build, with client-side routing
  root /var/www/nbr-crm;
  location / {
    try_files $uri $uri/ /index.html;
  }
}

Do not put the CRM on the public internet without restriction if you can avoid it. It is an internal system holding personal data. An IP allowlist, a VPN, or Cloudflare Access in front of it is worth the small inconvenience.

08 Changes on the existing website

The complete list. It is short on purpose — the customer-facing system keeps behaving exactly as it does today.

8.1 — Environment: nothing to change no action

The connector reads no environment variables. Every existing variable — DATABASE_URL, JWT_SECRET, the R2 keys, SMTP, Razorpay, Redis — stays exactly as it is. Nothing is added, removed or repurposed.

The reason is deliberate: the shared secret and the CRM address need to be changeable by an administrator without a redeploy, and rotating a secret should not require an ops ticket. They live in site_settings and are edited in the admin panel.

Two existing variables are worth confirming rather than changing, because the connector's deep links back into the site are built from them:

VariableConfirm it is
API_URLThe site's real public API address.
FRONTEND_URLThe site's real public address, so links the CRM shows open the right page.

8.2 — Deploy the connector branch action

Deploy the branch carrying the connector. It adds files and appends to a few existing route handlers; no existing endpoint changes its request or response shape, and no customer-facing behaviour is altered.

What it addsWhere
Signing, verification and push helpersbackend/src/lib/crmSync.ts, crmSyncPayload.ts
The connector routesbackend/src/routes/crmConnector.ts
One line each in approve, manual payment, certificate issue, payment settle, dispatch updateexisting route files
The Internal CRM settings tabsrc/pages/admin/AdminSettings.tsx, CrmSyncPanel.tsx

The hooks cannot break the site. Each is a single non-throwing, fire-and-forget call. If the CRM is down, unreachable or misconfigured, the approval or payment on the website still succeeds and the failure is written to the sync log.

8.3 — Run the migration action

cd backend
pnpm db:migrate

Additive only. It creates the crm_sync_log table and inserts three rows into site_settings — crm_sync_enabled (false), crm_base_url (empty), crm_secret (empty). No existing table is altered and no existing row is touched. With sync left off, the site behaves precisely as before.

8.4 — Allow outbound access action

The website's server must be able to reach the CRM over HTTPS, and the CRM must be able to reach the website. If you put the CRM behind an IP allowlist, add the website server's egress addresses to it.

8.5 — Check the clock action

Signatures are rejected outside a 300-second window. Confirm NTP is running on both servers. The Test connection button reports the measured difference, so you will know immediately if this is the problem.

09 Connecting the two

Do the CRM side first, so the website has something to talk to.

On the CRM

  1. Sign in as the Super Admin and change the temporary password.
  2. Open Settings and set the integration to the website's base URL (for example https://nationalbookofrecords.in), paste the same shared secret that is in NBR_WEBHOOK_SECRET, and switch it on.
  3. Run sync packages and sync categories so the CRM's dropdowns mirror the website's. Do this before anyone raises a payment — otherwise operators are offered prices the website will reject.

On the website

  1. Sign in to the admin panel and open Settings → Internal CRM.
  2. Enter the CRM base URL (for example https://crm.example.in) and the same shared secret. No trailing slash, no quotes, no stray whitespace.
  3. Switch sync on and save.
  4. Press Test connection. Compare the two secret fingerprints if it fails — if they differ, the secrets differ.
  5. Press Backfill to send every approved-and-beyond application. Safe to re-run; nothing is duplicated.

Backfill sends approved applications and everything past that point. Pending, under-review and draft applications are deliberately excluded — they belong to the website until somebody approves them.

10 Verifying the deployment

Work down this list before handing over. Each item has failed in testing at least once, which is why it is here.

The CRM alone
  • The API starts with no environment complaints.
  • Signing in works, and the first login forces a password change.
  • Changing the password signs you out everywhere, and the new one works.
  • Creating an applicant succeeds and the category list shows the website's categories.
  • Uploading a file succeeds and downloading it back returns the same file.
  • A test email arrives and is not marked as spam.
Website → CRM
  • Test connection reports success.
  • Approving an application on the website makes it appear in the CRM within seconds, at Selected.
  • Recording a manual payment on the website shows it in the CRM against the correct package and price.
  • Updating dispatch on the website updates the CRM's dispatch tab.
CRM → website
  • Recording a payment in the CRM shows it on the website's application.
  • Issuing a certificate in the CRM puts the number on the website.
  • Updating dispatch in the CRM mirrors the courier and tracking number.
  • An applicant created in the CRM does not appear on the website. This is correct.
The sync log
  • Settings → Internal CRM → sync log shows both directions with successful outcomes and no errors.

11 Backups, upgrades and rotation

Back up

WhatHow oftenNote
PostgreSQLDaily, retained per policyTest a restore before you need one.
Object storage bucketVersioning or scheduled copyCertificates and evidence are not reproducible.
PII_ENCRYPTION_KEYOnce, held securelyStore it apart from the database backup. A backup you cannot decrypt is not a backup.

Upgrading

git pull
pnpm install --frozen-lockfile
pnpm build
pnpm db:migrate        # additive; safe to re-run
# restart the API service

Redeploy apps/web/dist alongside it. Migrations are written to be additive, so the API can be restarted after they run without a maintenance window for most releases.

Rotating the shared secret

There is a brief window where the two sides disagree, so do this out of hours.

  1. Generate a new secret.
  2. Update NBR_WEBHOOK_SECRET in the CRM environment and restart the API.
  3. Update the CRM's own integration secret in Settings.
  4. Update the website's shared secret in Settings → Internal CRM.
  5. Press Test connection, then re-sync any application that failed during the gap.

Rotating the encryption key

Move the current PII_ENCRYPTION_KEY into PII_ENCRYPTION_KEY_PREVIOUS, put the new key in PII_ENCRYPTION_KEY, and restart. Existing rows stay readable through the previous key while the re-encryption job works through them. Clear the previous key only once it has finished.

12 Troubleshooting

SymptomCauseFix
API exits at startup with a list of variables Environment validation failed. Fix each line it names. It reports every problem at once.
JWT_REFRESH_SECRET must differ Both JWT secrets are the same value. Generate a second, different one.
COOKIE_SECURE must be true Production without TLS. Terminate TLS and set it to true. Do not disable the check.
Boot refuses on data region Database host outside the permitted region. Move the database to India. Do not weaken DPDP_DATA_REGION.
WEBHOOK_SIGNATURE_INVALID (401) The secrets differ, or a proxy rewrote the body. Compare fingerprints on both sides. Check for a second .env. Ensure the proxy does not modify request bodies.
timestamp outside tolerance Clock drift over 300 seconds. Fix NTP on both servers. Test connection shows the measured difference.
Sign-in succeeds then immediately fails SPA and API on different origins, so SameSite=strict cookies are dropped. Serve both from one hostname as in section 7.
Uploads fail on large files Proxy body limit below MAX_UPLOAD_MB. Raise client_max_body_size above 200 MB.
Payment push rejected by the website The package is CRM-only and has no plan code. Run the package sync so the catalogues match.
Everyone signed out at once Redis restarted or was flushed. Expected — sessions live in Redis. Users sign in again.
Duplicate evening sales reports More than one API instance running the scheduler. Run a single instance.

Where to look first

  1. Website → Settings → Internal CRM → sync log. Both directions, with the outcome and reason for each.
  2. The API log. Every failed push is logged with its HTTP status and the response body.
  3. CRM → Audit Logs. Confirms whether the action was recorded at all, and who performed it.
