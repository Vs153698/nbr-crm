One Applicant · One Profile

Every applicant gets one permanent digital profile. The full lifecycle — application → verification → payment → certificate → publication → dispatch — is managed from a single screen with tabs, quick actions and an auto-generated timeline.

GUIDED WORKFLOW

The system doesn't just store data. At every status, it surfaces the exact next actions the employee should take (send selection email, set payment deadline, upload certificate, add courier…), and logs everything automatically.

05Recommended Tech Stack

Built for speed: caching at every layer

A modern Node.js (TypeScript) stack — currently the fastest mainstream option for API-heavy CRUD systems like this — tuned aggressively for low GET/POST/PUT/DELETE latency. Every layer between the user's click and the database has a cache or a queue.

Frontend
React 18 + TypeScript + Vite — instant HMR in dev, tree-shaken ~180KB gzip production bundle.
TanStack QueryTanStack Table (virtualized)Tailwind CSSshadcn/uiReact Hook Form + ZodRechartsReact Router (lazy routes)
Why fast: TanStack Query gives stale-while-revalidate client caching — repeat visits to a profile render instantly from cache while re-fetching in background; optimistic updates make POST/PUT feel 0 ms; list virtualization keeps 10,000-row applicant tables at 60fps.
Backend
Node.js 22 LTS + TypeScript — NestJS 11 on the Fastify adapter — Fastify is consistently among the fastest Node frameworks (schema-compiled JSON serialization, ~2× Express throughput); NestJS adds the module/DI structure a long-lived CRM needs.

Why fast: the non-blocking event loop keeps I/O-bound CRUD requests in single-digit ms before DB; route schemas pre-compile validation & serialization; heavy work (PDF, exports, emails, thumbnails, imports) never blocks a request — it's queued on BullMQ.
Database

Why fast: every list filter and search hits an index — no sequential scans; trigram index makes "Rahul Ver…" search <10 ms even at 100k applicants; keyset pagination stays O(1) at any page depth.

Why not the alternatives

Laravel / PHP

Solid, but even with Octane it trails Fastify on raw throughput for this I/O-heavy workload, and a single TypeScript language across frontend + backend (shared Zod types, shared models) removes a whole class of contract bugs and speeds delivery.

MySQL

Acceptable fallback, but PostgreSQL's trigram search, partial indexes and JSONB (template variables, audit payloads) directly serve requirements §17–18 with no extra services like Elasticsearch.

Firebase / no-code

Fails the "permanent single source of truth, complex RBAC, immutable audit" requirements and locks NBR into per-read pricing at scale. Rejected.

06Database Architecture

Schema: one master profile, many records, immutable history

22 tables. The core rule from both documents is enforced at the schema level: applicants is the master person table; records (applications) hang off it — the same person applying again creates a new record, never a new person. Timeline and audit tables are append-only.

IDENTITY

People & Access

  • users — staff, role_id, status, last_login
  • roles / permissions / role_permission
  • applicants — master profile: NBRAP id, name, parents, DOB, gender, mobile, whatsapp, email, address, city, state, country, PIN, nationality, photo
LIFECYCLE

Records & Workflow

  • records — NBRR id, applicant_id, status, source, assigned_to, remarks
  • achievements — title, category_id, type, description, approved_description, date, location, participants
  • status_transitions — allowed from→to per role
  • timeline_events — append-only: record_id, actor, action, meta, at
MONEY & DOCS

Payments & Certificates

  • payments — package_id, amount, gst, discount, final, status, due_date
  • payment_transactions — partial/multiple payments, txn_id, receipt_file
  • invoices — number series, pdf_file
  • certificates + certificate_versions — immutable versions, pdf + editable file
EVERYTHING ELSE

Ops & Governance

  • evidence_files / attachments — R2 keys, kind, size, uploaded_by
  • publications · dispatches
  • notes (with edit history) · tasks
  • communications — channel, template_id, rendered body, sent_by
  • templates · blacklists · flags
  • notifications · audit_logs (append-only) · settings

Index & integrity strategy

ConcernImplementation
Global search (§17)pg_trgm GIN index on applicants(name, mobile, email) + records(record_no) + certificates(certificate_no); single /search?q= endpoint fans out with UNION, <10 ms.
List filters (§3)Composite indexes: records(status, assigned_to, updated_at), payments(status, due_date), dispatches(delivery_status). Partial index on hot queues, e.g. WHERE status='payment_pending'.
Duplicate detection (§18)Unique-ish probes on normalized mobile/email + fuzzy name+DOB via trigram similarity ≥ 0.6; blacklist join at insert time; DB-level unique constraint on applicants(mobile) soft-guarded with admin override path.
Immutability (§13, §23)timeline_events, audit_logs, certificate_versions: no UPDATE/DELETE grants to app role; Postgres rule + application guard. Files: versioned keys in R2, deletes disabled.
Money correctnessAmounts as NUMERIC(12,2); final amount computed and checked (amount + GST − discount); payment status derived from SUM(transactions) vs final — partial payments supported natively.
ConcurrencyStatus changes use optimistic locking (updated_at check) so two staff can't double-transition a record; queue jobs idempotent by event id.

12Quality, Security, Deployment & Handover

How we make sure it works — and keeps working

A CRM holding payments, certificates and legal history cannot afford data loss or downtime. This section is the operational contract: what gets tested, how the system is secured, how it goes live, and what NBR receives at handover.

Testing plan

FUNCTIONAL

Workflow regression suite

Automated tests (Vitest/Supertest + Playwright) walk a dummy applicant through the entire lifecycle — New Lead → Completed — asserting at each step that the right status transitions are offered, the right emails queue, the timeline logs the event, and invalid jumps are rejected. Runs on every code push via GitHub Actions; a red build cannot be deployed.

PERMISSIONS

Role × action test matrix

All 7 roles are tested against every sensitive action (view payments, edit certificate, blacklist, delete draft, export, settings). Each cell of the matrix is an automated API test asserting 403 Forbidden where access must be denied — so a Viewer can never see revenue and only Super Admin can override a blacklist.

PERFORMANCE

k6 load test before go-live

Seeded with 25,000 applicants and 100,000 timeline events, we run k6 scenarios (50 concurrent staff, mixed read/write) and verify the latency budget from §7: p95 GET < 150 ms, writes < 250 ms, dashboard TTI < 1 s. Any query breaching budget gets an index or cache before launch.

DATA SAFETY

Integrity checks

Tests assert the invariants that protect NBR legally: timeline and audit logs are append-only (no UPDATE/DELETE possible), certificate versions are never overwritten, payments can never exceed package total, and blacklisted applicants are blocked from new applications at the database level, not just the UI.

Security hardening

LayerMeasures
AuthenticationArgon2id password hashing · JWT in HttpOnly cookies with Redis-revocable refresh tokens · login rate-limiting & lockout after 5 failures · forced password change on first login · session revocation from Users screen.
AuthorisationEvery API route wrapped in role/permission guards (CASL policies). Server is the source of truth — hiding a button in the UI is never the only guard.
DataTLS everywhere (Cloudflare) · files served only via short-lived presigned URLs (no public bucket) · PII access logged to audit_logs · daily encrypted off-site backups to R2 with 30-day retention · restore drill performed before go-live.
ApplicationValidation on every input (server-side) · CSRF protection · SQL injection impossible via Drizzle parameterised queries · file uploads MIME-checked & virus-scanned · Sentry alerts on any 5xx spike.
InfrastructureVPS firewall: only 80/443 public, SSH key-only · Docker containers run non-root · dependency scanning (Dependabot) · secrets in environment vault, never in code.
