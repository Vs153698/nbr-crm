National Book of Records

Local development · Two-system setup

Running both systems on your machine

There are two applications. The existing system runs the public website, the applicant portal and the current admin panel — it is unchanged and still owns everything customer-facing. The new CRM is the internal management tool. This guide gets both running side by side and connects them.

01 How the two fit together

Read this first — it explains why the setup has the shape it does.

Existing system unchanged

Public site, applicant portal, applications, payments, certificates, awardee pages. Remains the system of record for everything a customer sees.

⇄
New CRM internal

One applicant, one profile, every record. Approved applications appear here with their payment, certificate and dispatch state — and can be managed from here.

Nothing about the existing system's own behaviour changed. A set of connectors was added to it: an outbound push that mirrors approved applications into the CRM, and a small inbound API the CRM calls when something is updated on its side. With the connector switched off — which is the default — the existing system behaves exactly as it did before.

WhatExisting → CRMCRM → Existing
Application (on approval)✅ pushed— records created only in the CRM stay there
Payment received✅ pushed✅ pushed back
Certificate issued✅ pushed, with its verification link✅ pushed back
Dispatch & tracking✅ pushed✅ pushed back
Awardee page✅ link shown in the CRM— created and published on the site
Approved and beyond

Only applications that reached approved are mirrored. Pending, rejected and cancelled applications stay solely in the existing system, which is where that part of the workflow lives.

node --version      # v22.x or newer

The two systems need separate databases

They have completely different schemas. The new CRM brings its own Postgres in Docker on port 5434; the existing system needs a Postgres of its own (its default is 5432). Do not point them at the same database.

03 Start the new CRM nbr-crm

Roughly five minutes the first time. Everything it depends on runs in Docker.

  1. Install dependencies

    cd nbr-crm
pnpm install

  2. Create the environment file

    Copy the template, then fill in the secrets it asks for. The API refuses to start on a missing or placeholder secret rather than failing later on the first request that needs it.

    cp .env.example .env

    Generate real values and paste them in:

    openssl rand -base64 48   # JWT_ACCESS_SECRET
openssl rand -base64 48   # JWT_REFRESH_SECRET  (must differ)
openssl rand -base64 32   # PII_ENCRYPTION_KEY
openssl rand -hex 32      # NBR_WEBHOOK_SECRET  ← keep this one, you need it in §5
    NBR_WEBHOOK_SECRET is the link between the two systems

    It signs every request in both directions. Write it down now — the same value goes into the existing system's settings screen in step 5.

  3. Build the shared package

    Both the API and the web app import @nbr/shared, and the migration scripts will not run until it has been built once.

    pnpm --filter @nbr/shared build

  4. Start Postgres, Redis, MinIO and Mailpit

    pnpm infra:up

    The script waits for each service and tells you when they are ready.

  5. Create the file storage bucket

    Once only. Evidence uploads fail without it.

    docker run --rm --network nbr-crm_default --entrypoint sh minio/mc:latest -c \
  "mc alias set local http://nbr-minio:9000 nbr_minio nbr_minio_password && \
   mc mb --ignore-existing local/nbr-vault && mc anonymous set none local/nbr-vault"

    Or create a bucket named nbr-vault from the MinIO console at http://localhost:9001.

  6. Apply migrations and seed

    The seed is idempotent — safe to re-run any time. It creates roles, permissions, statuses, categories, packages, couriers, templates and the Super Admin.

    pnpm db:migrate
pnpm db:seed

  7. Run it

    pnpm dev              # API on :4100, web on :5173

    Or one at a time: pnpm dev:api and pnpm dev:web.

    Do not run the API with tsx

    esbuild does not emit decorator metadata, which NestJS dependency injection requires. Use pnpm dev:api, or nest build && node dist/main.js. The migration and seed scripts have no decorators and run fine under tsx.

Working

Open http://localhost:5173 and sign in with the Super Admin credentials from your .env. The API reference is at http://localhost:4100/api/docs, and any mail the CRM sends lands in Mailpit at http://localhost:8025 instead of a real inbox.

04 Start the existing system nationalbookofrecord

Two processes: a Fastify API and a Vite frontend. Use the connect-to-main-crm branch, which carries the connector.

  1. Check out the connector branch

    cd nationalbookofrecord
git checkout connect-to-main-crm

  2. Create its database

    Any Postgres 16 will do. If you would rather not install one, reuse the container the CRM already started — just give it a separate database:

    # Option A — reuse the CRM's Postgres container, separate database
docker exec nbr-postgres psql -U nbr -d postgres -c "CREATE DATABASE legacy_nbr;"
docker exec nbr-postgres psql -U nbr -d legacy_nbr -c 'CREATE EXTENSION IF NOT EXISTS "uuid-ossp";'
    # Option B — your own local Postgres on :5432
createdb nbr_db
psql -d nbr_db -c 'CREATE EXTENSION IF NOT EXISTS "uuid-ossp";'

  3. Configure the backend

    cd backend
cp .env.example .env

    The minimum needed to boot locally:

    PORT=3001
NODE_ENV=development
# Option A (CRM's container):
DATABASE_URL=postgresql://nbr:nbr_dev_password@localhost:5434/legacy_nbr
REDIS_URL=redis://localhost:6380
# Option B (your own Postgres/Redis):
# DATABASE_URL=postgresql://postgres:password@localhost:5432/nbr_db
# REDIS_URL=redis://localhost:6379

JWT_SECRET=change-me-minimum-32-characters-long
FRONTEND_URL=http://localhost:3000
MIGRATE_STORAGE_ON_BOOT=false

    R2, Razorpay, SMTP and WhatsApp keys can stay blank for local work — those features are simply inert without them.

  4. Run the backend

    It migrates its own schema on every start, so there is no separate migrate step.

    npm install
npm run dev           # API on :3001

  5. Run the frontend

    In a second terminal, from the repository root:

    npm install
npm run dev           # site + admin on :3000, proxying /api → :3001

  6. Create an admin account

    Seed the demo data, which includes a Super Admin:

    cd backend
npm run db:seed

05 Connect them existing → CRM

Done entirely from the existing admin panel. No redeploy, no environment variable.

Step 1
Open the settings

Sign in to the admin panel at localhost:3000, go to Settings → Internal CRM.

Step 2
Fill in the connection

Base URL: http://localhost:4100 — no trailing slash. Shared secret: the NBR_WEBHOOK_SECRET from §3. Tick Enabled, then Save Changes.

Step 3
Test the connection

Press Test Connection. It pushes one real application and reports what the CRM answered — not just a URL format check.

Step 4
Sync everything across

Press Sync All Existing Applications. Progress appears on the screen as it runs. Safe to repeat — the CRM ignores anything it already has.

From this point on, every application you approve in the existing admin panel appears in the CRM within a second or two, carrying its evidence links, its payment, its certificate number and its courier details.

What "Sync All" actually sends

Every approved application, oldest first, each as a complete snapshot of its current state. An application that is already paid, certified and delivered arrives in the CRM at Delivered — with its payment, certificate and courier row — rather than back at the start of the workflow.

Clock drift breaks signatures

Every request is signed with a timestamp, and anything more than five minutes old is rejected as a replay. If pushes suddenly start failing with a 401, check the clock on both machines before anything else.

06 Enable the return path CRM → existing

So that a payment, certificate or dispatch recorded in the CRM also lands on the public site. Configured from the CRM's own settings.

  1. Open Settings in the CRM

    At localhost:5173, go to Settings and find the Integrations section.

  2. Point it back at the existing system

    SettingValue
    integrations.legacy.base_urlhttp://localhost:3001
    integrations.legacy.secretthe same NBR_WEBHOOK_SECRET
    integrations.legacy.enabledtrue

  3. That is all

    Record a payment, upload a certificate or update a courier in the CRM, and it is written into the existing system too. Check GET /api/v1/integrations/nbr-website/push-status to see whether anything is failing.

Only records that came from the website are pushed back

A record created directly in the CRM has no counterpart on the public site, so nothing is sent for it — which is the intended behaviour for the older data you are entering only in the CRM.

Applicant-facing email for a CRM-recorded payment is sent by the CRM, not by the website, so the applicant gets one message rather than two.

Mail from the CRM

SMTP can be set from the same Settings screen, under Mail. Any field left blank keeps the value the server booted with, so you can override just the host or just the From address. Send a test email sends a real message with the saved settings rather than only opening a connection — a relay that authenticates but rejects your From address fails here rather than silently on the first certificate email.

07 Verify it works

Five checks that together prove both directions. Each one is quick.

  1. Both systems answer

    curl -s http://localhost:3001/health          # existing → {"status":"ok",…}
curl -s http://localhost:4100/health          # CRM      → {"status":"ok",…}

  2. An approval reaches the CRM

    Approve an application in the existing admin panel. Within a couple of seconds it should appear in the CRM's applicant list. If it does not, look at Settings → Internal CRM → Recent Sync Activity — a failed push is logged there with the HTTP status and the reason.

  3. The whole lifecycle carries across

    Record a payment on that application in the existing panel, then issue a certificate, then add courier details. Each one should move the CRM record forward — Payment Received, then Certificate Uploaded, then Dispatched — with a timeline entry attributed to the integration.

  4. The return path writes back

    In the CRM, mark the dispatch delivered. Refresh the existing system's Dispatch screen — the same order should now read delivered.

  5. Nothing is duplicated

    After all of the above, the CRM record should hold exactly one payment, one certificate and one dispatch — not one per event. Every push is a full snapshot, and repeated or replayed deliveries are recognised and skipped.

Verified end to end

This flow was driven against a live stack: five lifecycle pushes produced one record at Delivered with exactly one payment, one certificate and one dispatch; an identical redelivery was skipped; a stale snapshot did not roll the status back; and unsigned, wrongly signed and replayed requests were all rejected with a 401.

09 Troubleshooting

The failures you are most likely to hit, and what each one actually means.

SymptomCause and fix
CRM API exits on start complaining about a secret A value in .env is missing or still a placeholder. Generate real ones with the openssl commands in §3. The API refuses to boot rather than fail later on the first request that needs the key.
Cannot find module @nbr/shared Run pnpm --filter @nbr/shared build. Both apps import it and it is not built automatically on install.
Nest cannot resolve a dependency Almost always the API being run under tsx. Use pnpm dev:api.
Test Connection returns 401 The secret differs between the two systems, or a clock is more than five minutes out. Re-paste the secret; check the time.
Test Connection says there are no applications Nothing has reached approved yet. Approve one, or seed the existing system.
Evidence uploads fail in the CRM The nbr-vault bucket does not exist. Create it — §3, step 5.
Imported record filed under "Other" Its category name has no match in the CRM's list. A notification is raised so it can be corrected; rename the category, or add the matching one under Settings.
An approval did not reach the CRM Settings → Internal CRM → Recent Sync Activity in the existing panel shows every push with its HTTP status and error. Approval itself is never blocked by a failed push, so the application is safe — it just needs re-sending.
Port already in use Another project is holding a default port. Both systems read their ports from .env — change the one that clashes.
Never point both systems at one database

The schemas are unrelated. The existing system migrates its own tables on every start, and letting it do that inside the CRM's database will not end well. Keep them separate — a second database in the same container is fine.
