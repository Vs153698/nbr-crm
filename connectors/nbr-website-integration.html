Connecting your existing NBR website to the CRM

When an application is approved in your current NBR admin panel, it should appear in the CRM automatically — master applicant created or merged, record opened, evidence copied across, team notified. No re-typing. This document is the contract your developer builds against.

01 How it works

Your website pushes; the CRM pulls only as a fallback. Push is preferred because it is immediate and costs nothing when nothing is happening.

STEP 1 Approval on your site A staff member approves an application in the existing NBR admin panel.
STEP 2 Your site POSTs to the CRM One signed HTTPS request carrying the applicant, achievement, evidence links and consent.
STEP 3 CRM verifies & queues Signature and timestamp checked, payload stored, 202 Accepted returned in under 50 ms.
STEP 4 CRM imports Duplicate and blacklist checks run, applicant created or merged, record opened, timeline written.
Why the CRM answers before it finishes importing

The import copies evidence files, runs fuzzy duplicate matching and writes several tables. Doing that inside the HTTP request would make your admin panel wait seconds on every approval, and a slow CRM would start failing approvals on your side. Instead the CRM durably stores the payload, answers 202, and processes it on a queue. Your site's only job is to get a 2xx.

The shared secret is a credential

We will send you a secret out of band. It goes in your server's environment configuration — never in a Git repository, never in front-end JavaScript, never in a WordPress post-meta field. Anyone holding it can create applicant records in your CRM.

If you think it has leaked, tell us and we will rotate it. Rotation is a two-minute change on both sides.

04 Signing the request

The signature proves the request came from your website and that nobody altered it in transit. It takes about six lines of code.

  1. Serialise the body once Build the JSON string and keep that exact string. Sign it and send it — do not re-encode between the two, or the byte order changes and the signature stops matching.
  2. Take the current Unix timestamp In seconds, not milliseconds.
  3. Build the signing payload <timestamp> + "." + <raw JSON body>
  4. HMAC-SHA256 it with the shared secret Output as lowercase hex.
  5. Send both in the header X-NBR-Signature: t=1785312000,v1=a3f5…
Why the timestamp is inside the signature

Without it, a captured request stays valid forever — anyone who records one could replay it next month and create a duplicate record. Because the timestamp is signed, it cannot be edited, and the CRM rejects anything more than 5 minutes old.

This means your server clock matters. If it drifts more than five minutes, every request will be rejected. Keep NTP running.

Please send consent if you have it

Under the DPDP Act, 2023, NBR must be able to show when and for what each applicant consented. If your site captured that, sending it preserves the real timestamp. If you omit it, the CRM records consent as given at import time by staff — which is weaker evidence and means someone may have to chase the applicant again later.

06 Code examples

Complete, copy-paste-able senders including the signature.

<?php
/**
 * Send an approved application to the NBR CRM.
 * Returns true on success. Never lets a CRM outage break your approval flow.
 */
function nbr_crm_send_application(array $payload): bool {
    $baseUrl = getenv('NBR_CRM_URL');      // https://crm.nbr.in
    $secret  = getenv('NBR_CRM_SECRET');   // shared secret — env only

    // 1. Serialise ONCE and reuse the exact string. Re-encoding would change
    //    key order and break the signature.
    $body = json_encode($payload, JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE);

    // 2-4. Sign "<timestamp>.<body>" with HMAC-SHA256.
    $timestamp = time();
    $signature = hash_hmac('sha256', $timestamp . '.' . $body, $secret);

    $ch = curl_init($baseUrl . '/api/v1/integrations/nbr-website/applications');
    curl_setopt_array($ch, [
        CURLOPT_POST           => true,
        CURLOPT_POSTFIELDS     => $body,
        CURLOPT_RETURNTRANSFER => true,
        CURLOPT_TIMEOUT        => 15,
        CURLOPT_HTTPHEADER     => [
            'Content-Type: application/json',
            "X-NBR-Signature: t={$timestamp},v1={$signature}",
            "X-NBR-Idempotency-Key: {$payload['externalId']}",
        ],
    ]);

    $response = curl_exec($ch);
    $status   = curl_getinfo($ch, CURLINFO_HTTP_CODE);
    curl_close($ch);

    if ($status >= 200 && $status < 300) {
        return true;
    }

    // Log and move on. The approval already succeeded on your side; a CRM
    // hiccup must not roll it back. Queue a retry — the same externalId is
    // safe to send again.
    error_log("NBR CRM sync failed ({$status}): {$response}");
    return false;
}

function nbr_push_to_crm($application_id) {
    $post = get_post($application_id);
    $meta = get_post_meta($application_id);

    $payload = [
        'externalId'  => (string) $application_id,
        'externalUrl' => get_edit_post_link($application_id, ''),
        'approvedAt'  => gmdate('c'),
        'applicant' => [
            'fullName' => $meta['applicant_name'][0] ?? '',
            'mobile'   => $meta['mobile'][0] ?? '',
            'email'    => $meta['email'][0] ?? '',
            'city'     => $meta['city'][0] ?? null,
            'country'  => 'India',
        ],
        'achievement' => [
            'recordTitle' => $post->post_title,
            'category'    => $meta['category'][0] ?? null,
            'description' => wp_strip_all_tags($post->post_content),
        ],
        'evidence' => array_map(fn($id) => [
            'url'         => wp_get_attachment_url($id),
            'fileName'    => basename(get_attached_file($id)),
            'contentType' => get_post_mime_type($id),
        ], get_attached_media('', $application_id)),
    ];

    $body      = wp_json_encode($payload);
    $timestamp = time();
    $signature = hash_hmac('sha256', "$timestamp.$body", NBR_CRM_SECRET);

    // Non-blocking so the editor never waits on the CRM.
    wp_remote_post(NBR_CRM_URL . '/api/v1/integrations/nbr-website/applications', [
        'headers'  => [
            'Content-Type'            => 'application/json',
            'X-NBR-Signature'         => "t=$timestamp,v1=$signature",
            'X-NBR-Idempotency-Key'   => (string) $application_id,
        ],
        'body'     => $body,
        'timeout'  => 15,
        'blocking' => false,
    ]);
}
<?php
namespace App\Services;

use Illuminate\Support\Facades\Http;
use Illuminate\Support\Facades\Log;

class NbrCrmSync
{
    public function send(array $payload): bool
    {
        $body      = json_encode($payload, JSON_UNESCAPED_SLASHES);
        $timestamp = time();
        $signature = hash_hmac('sha256', "{$timestamp}.{$body}", config('services.nbr_crm.secret'));

        $response = Http::withBody($body, 'application/json')
            ->withHeaders([
                'X-NBR-Signature'       => "t={$timestamp},v1={$signature}",
                'X-NBR-Idempotency-Key' => $payload['externalId'],
            ])
            ->timeout(15)
            // Exponential backoff. The same externalId is always safe to resend.
            ->retry(3, 2000, throw: false)
            ->post(config('services.nbr_crm.url') . '/api/v1/integrations/nbr-website/applications');

        if ($response->successful()) {
            return true;
        }

        Log::error('NBR CRM sync failed', [
            'status'     => $response->status(),
            'body'       => $response->body(),
            'externalId' => $payload['externalId'],
        ]);

        return false;
    }
}
import { createHmac } from 'node:crypto';

export async function sendToNbrCrm(payload) {
  // Serialise once — sign and send the identical string.
  const body = JSON.stringify(payload);
  const timestamp = Math.floor(Date.now() / 1000);

  const signature = createHmac('sha256', process.env.NBR_CRM_SECRET)
    .update(`${timestamp}.${body}`)
    .digest('hex');

  const response = await fetch(
    `${process.env.NBR_CRM_URL}/api/v1/integrations/nbr-website/applications`,
    {
      method: 'POST',
      headers: {
        'content-type': 'application/json',
        'x-nbr-signature': `t=${timestamp},v1=${signature}`,
        'x-nbr-idempotency-key': payload.externalId,
      },
      body,
      signal: AbortSignal.timeout(15_000),
    },
  );

  if (!response.ok) {
    const detail = await response.text();
    throw new Error(`NBR CRM sync failed (${response.status}): ${detail}`);
  }

  return response.json();
}
import hashlib, hmac, json, os, time
import requests

def send_to_nbr_crm(payload: dict) -> dict:
    """Send one approved application. Raises on a non-2xx response."""
    # Serialise once; sign and send the identical bytes.
    body = json.dumps(payload, separators=(',', ':'), ensure_ascii=False)
    timestamp = int(time.time())

    signature = hmac.new(
        os.environ['NBR_CRM_SECRET'].encode(),
        f'{timestamp}.{body}'.encode(),
        hashlib.sha256,
    ).hexdigest()

    response = requests.post(
        f"{os.environ['NBR_CRM_URL']}/api/v1/integrations/nbr-website/applications",
        data=body.encode(),
        headers={
            'Content-Type': 'application/json',
            'X-NBR-Signature': f't={timestamp},v1={signature}',
            'X-NBR-Idempotency-Key': payload['externalId'],
        },
        timeout=15,
    )
    response.raise_for_status()
    return response.json()

07 Field mapping

Fill the middle column with your field names and send this table back — that is the workshop the plan budgets for, and it takes about twenty minutes.

CRM fieldYour fieldNotes

applicant.fullName_______________Required. If you store first/last separately, join them.
applicant.mobile_______________Required. Any format — we strip +91, spaces and dashes.
applicant.email_______________Required. Used for duplicate matching.
applicant.dateOfBirth_______________Strongly recommended — it sharpens duplicate detection, and it is how we detect applicants under 18.

achievement.category_______________Send the category name. We match it to ours; an unmatched name lands in "Other" and flags the record for review rather than failing the import.

consent.acceptedAt_______________The real timestamp from your terms checkbox, if you have it.
What happens to a returning applicant

If the mobile, email or name+DOB matches someone already in the CRM, the import adds a new record to their existing profile rather than creating a second one. That is the core rule of the system — one person, one permanent profile, however many records they hold. You do not need to do anything to make this work.

08 Responses & retries

CodeMeaningWhat your site should do
202Accepted, queuedDone. Mark it synced.
200Already importedA duplicate of a previous send. Also success — mark it synced.
400Malformed JSONBug on the sending side. Do not retry; fix and resend.
401Bad signatureWrong secret, or a clock more than 5 minutes out. Do not retry blindly.
422Validation failedThe response names the offending fields. Fix the mapping, then resend.
429Rate limitedBack off and retry after the Retry-After header.
5xxCRM problemRetry with exponential backoff. Same externalId — retries are safe.
Retrying is always safe

Every request is keyed on externalId with a database-level unique constraint. Send the same approval fifty times and exactly one applicant record exists. Build your retry loop without worrying about duplicates.

A sensible retry schedule

Immediate, then 1 min, 5 min, 30 min, 2 h, then give up and raise an alert. Anything still failing after two hours needs a human, not another retry.

09 Polling fallback

Only needed if your admin panel genuinely cannot make outbound HTTPS calls — some shared hosting blocks it.

In that case you expose a read-only endpoint and the CRM polls it every 5 minutes. You would provide: 

GET https://nationalbookofrecords.in/api/approved-applications?since=<ISO timestamp>
Authorization: Bearer <token you issue to us>

{ "applications": [ /* same shape as §5, newest last */ ] }
Push is better where you have the choice

Polling means an approval can sit up to five minutes before staff see it, and the CRM queries your server 288 times a day whether or not anything changed. Use it only as a fallback.

10 Testing

Verify your signature before sending anything

This is where nearly every integration stalls. Confirm your code produces the same digest as ours, using a fixed timestamp and body: 

# Both of these must print the identical hex string.

# Shell
printf '1785312000.{"externalId":"TEST-1"}' \
  | openssl dgst -sha256 -hmac "your-shared-secret" -r

# PHP
php -r 'echo hash_hmac("sha256", "1785312000." . "{\"externalId\":\"TEST-1\"}", "your-shared-secret");'

Then send a real test payload to staging

SECRET="your-shared-secret"
BODY='{"externalId":"TEST-001","applicant":{"fullName":"Test Applicant","mobile":"9000000001","email":"test@example.com","country":"India"},"achievement":{"recordTitle":"Integration test record"}}'
TS=$(date +%s)
SIG=$(printf "%s.%s" "$TS" "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -r | cut -d' ' -f1)

curl -i -X POST https://staging.nbr-crm.in/api/v1/integrations/nbr-website/applications \
  -H "content-type: application/json" \
  -H "x-nbr-signature: t=$TS,v1=$SIG" \
  -d "$BODY"
  1. Signature matches — the two commands above print the same hex.
  2. Staging accepts it — you get 202.
  3. It appears in the CRM — we confirm the applicant shows up with the right fields.
  4. Resend the same payload — you get 200, and still exactly one record.
  5. Send a deliberately bad signature — you get 401. Confirms the guard works.
  6. Send a returning applicant — same mobile, different record title. It should attach to the existing profile.
  7. Approve one real application end to end on staging, with real evidence files.
